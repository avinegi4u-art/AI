# Testing strategy

## The central choice: real datastores, not stubs

Tests run against a real PostgreSQL with PostGIS and a real Redis. This is the most consequential
testing decision in the repository, and it is deliberate.

The behaviour that matters most in this system *is* datastore behaviour:

- Distance ranking and polygon containment are PostGIS semantics.
- Timezone-aware opening hours, including windows past midnight, are a SQL expression.
- `FOR UPDATE SKIP LOCKED` claim semantics in the outbox relay only exist in a real database.
- Atomic token-bucket rate limiting is a Lua script executed by Redis.
- Unique constraints, `CHECK` constraints and cascade deletes are schema behaviour.

A mocked session would verify that the mock was called, which is a test of the test. Several
real bugs in this repository were caught only because the datastore was real: a `VARCHAR(20)`
overflow from a placeholder value, an insert-ordering violation across five tables, a geography
column recomputed from stale scalars, and an autogenerated migration that emitted DDL dropping
another service's table.

The cost is that the suite needs infrastructure. That is paid once in CI configuration, and it
buys tests whose passing means something.

## Levels

### Unit tests — pure logic, no I/O

The domain rules that must be exhaustively correct, tested as pure functions:

- **Money** — half-up rounding, currency exponents including three-decimal dinars, basis-point
  application, round-trip stability.
- **Identifiers** — uniqueness at scale, time-ordering (2,000 generated ids must be unique and
  lexicographically sorted by creation time), malformed-input rejection.
- **Phone normalisation** — seven input spellings of one UAE number all collapse to one
  canonical form, which is what stops a user from having two accounts.
- **Geo** — haversine against known Abu Dhabi landmark distances, bounding-box degeneration at
  the pole.
- **Basket validation** — every rule gets its own test rather than being covered incidentally:
  unknown item, cross-merchant item, unavailable item, unavailable option, option from the wrong
  group, group from the wrong item, too few, too many, and a required group omitted entirely.
- **ETA estimation** — monotonic in distance, never shorter than prep time.
- **The gateway route table** — parametrised over every path, including the two that route to
  catalog despite living under `/merchants`.

### Integration tests — one service against real infrastructure

Each service's suite drives its HTTP surface with `httpx.ASGITransport` against a real database
and Redis. Marked `integration` so `make test-unit` can skip them.

Authentication is real in the auth suite (tokens are minted and verified) and stubbed by
dependency override elsewhere, because those suites are about their own domain, not about JWT
verification, which the core suite already covers.

What these tests are actually for is failure paths:

```python
async def test_reuse_detection_revokes_the_whole_session(client, login):
    initial = await login()
    rotated = (await client.post("/auth/refresh", json={"refresh_token": initial["refresh_token"]})).json()

    # An attacker replays the stolen, already-rotated token.
    await client.post("/auth/refresh", json={"refresh_token": initial["refresh_token"]})

    # The legitimate holder's current token is now dead too: theft becomes a detected
    # incident and forces re-authentication rather than granting silent access.
    victim = await client.post("/auth/refresh", json={"refresh_token": rotated["refresh_token"]})
    assert victim.status_code == 401
```

### Migration-parity tests

Every service has one test that drops its schema, runs `alembic upgrade head`, and asserts the
result is identical to the models via `compare_metadata`.

This closes a specific and common gap. Test tables are created from metadata for speed, so a
model change with no accompanying migration would leave the entire suite green while every
deployed environment breaks. This test fails instead, with a message telling you which command
to run.

The migrations are also exercised in both directions: `downgrade base` then `upgrade head`.

### Contract tests

- Every registered event type resolves to a topic. Adding an event type without registering its
  prefix fails here rather than at runtime.
- The event envelope round-trips through JSON unchanged, and rejects naive timestamps and
  unknown fields.
- The OpenAPI documents are generated and committed; `python scripts/export_openapi.py --check`
  fails CI when they are stale, so an unintended contract change shows up as a diff in review.

### End-to-end smoke test

`scripts/smoke_test.py` drives the real customer journey through the running gateway: browse,
request an OTP, log in, read a profile, add an address, check serviceability, fetch a menu,
confirm the cached read matches, validate a good basket and a bad one, rotate a refresh token,
replay it and be rejected.

Nineteen steps, each reported pass or fail. It is the answer to "does this actually work
together", which no amount of per-service testing establishes.

## Conventions

**Test names are assertions.** `test_reuse_detection_revokes_the_whole_session`, not
`test_refresh_2`. A failure name should tell you what broke without opening the file.

**Comments explain why a case matters**, not what the code does:

```python
# 01:00 local on Tuesday is still inside *Monday's* window. This is the case naive
# implementations get wrong: the matching row is stored against the previous day.
assert await is_open(engine, merchant.id, TUESDAY_ONE_AM_LOCAL) is True
```

**Time is injected, never read from the clock.** Opening-hours tests pin the evaluation instant.
A test that depends on when the suite runs passes for most of the day and fails mysteriously at
2 a.m.

**Sample data is realistic and shared.** Real Abu Dhabi coordinates and a real Emirati menu, in
each service's `testing.py`, used by both the tests and the seed script. Synthetic grids hide
bugs that real geography exposes — a swapped longitude/latitude pair looks fine at `(0, 0)`.

**Isolation by truncation, not by transaction rollback.** Tables are truncated between tests and
Redis is flushed. Wrapping each test in a rolled-back transaction would break the code under
test, which manages its own transaction boundaries deliberately.

**Fixtures compose small.** `client`, `client_as(principal)`, `client_factory(**settings)`,
`seed_menu`, `merchant_factory` — so a test that needs a different policy or a different role
does not need its own app wiring.

## Running

```bash
make test         # everything
make test-unit    # only tests needing no external services
make coverage     # with a coverage report
make check        # lint, type-check, test — what CI runs
```

Requires PostgreSQL with PostGIS and Redis. The suite uses a separate `marsool_test` database
and Redis database 15, so it never touches development data.

## Current state

340+ tests. Every service, the shared library and the gateway. `ruff` and `mypy --strict`
clean across all source packages.

## Gaps, named

- **No load testing yet.** The search path is designed around indexes, but that is an argument,
  not a measurement. A k6 profile against seeded data belongs in Step 2.
- **No chaos testing.** Fail-open and fail-closed paths are unit-tested with a broken client
  stub, but not against a real Redis being killed mid-request.
- **No property-based tests.** Money arithmetic and the state machine are the two places
  Hypothesis would earn its keep.
- **No mutation testing.** The most honest way to find out whether these tests would actually
  catch a regression.
