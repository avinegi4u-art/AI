# Data stores

## PostgreSQL 16 with PostGIS — transactional and geospatial

The system of record for every service. One instance in the MVP, one logical schema per
service, no cross-schema reads or foreign keys. Splitting schemas across clusters later is an
infrastructure change, not a rewrite.

PostGIS is not optional infrastructure here, it is load-bearing. Merchant discovery answers
proximity, polygon containment and open-now in a single indexed query. The `geography` type is
used rather than `geometry` so distances come back in metres without any projection step:

```sql
SELECT m.*, ST_Distance(m.location, :point) AS distance_m
  FROM merchant.merchants m
 WHERE m.status = 'ACTIVE'
   AND ST_DWithin(m.location, :point, :radius_m)   -- GiST index-assisted
 ORDER BY distance_m, m.id                          -- unique tiebreaker for keyset paging
```

### Indexing

| Index | Table | Purpose |
|---|---|---|
| GiST on `location` | `merchant.merchants`, `identity.addresses` | Proximity and containment |
| GiST on `boundary` | `merchant.service_areas` | Polygon coverage |
| GIN on `cuisines` | `merchant.merchants` | Array overlap for the cuisine filter |
| GIN on `tags` | `catalog.menu_items` | Dietary and attribute filters |
| `(status, accepting_orders)` | `merchant.merchants` | Narrow to bookable merchants before ranking |
| `(merchant_id, day_of_week)` | `merchant.merchant_hours` | The open-now correlated subquery |
| `(user_id, created_at)` | `identity.addresses` | A user's address list |
| `(status, created_at)` | `*.event_outbox` | The relay's claim query |

Primary keys are prefixed ULIDs, which are time-sortable, so inserts stay at the right edge of
the B-tree instead of scattering across it.

### Conventions

- Money as integer minor units (`BIGINT`), never `FLOAT` or `NUMERIC` for amounts.
- Coordinates stored twice on purpose: `NUMERIC(9,6)` scalars are what clients read and write,
  the `geography` column is what queries use. The derived column is recomputed whenever either
  scalar changes — a bug we shipped and fixed once already.
- Enums as `VARCHAR` with a `CHECK` constraint, so adding a variant is a code change rather
  than a locking `ALTER TYPE`.
- Timestamps are `TIMESTAMPTZ`, generated by the database, so ordering survives clock skew
  between replicas.
- Deterministic constraint naming, which keeps Alembic autogenerate output stable.

## Redis — cache, rate limits, idempotency

One Redis instance, three uses with deliberately different failure semantics:

| Use | On Redis failure | Why |
|---|---|---|
| Menu and search caching | **Fail open** (treat as a miss) | A cache outage must not become a platform outage |
| Rate limiting | **Fail open** (allow) | Rejecting all traffic because the limiter is down turns a degradation into an outage |
| OTP attempt counting | **Fail closed** (refuse) | Unlimited guesses against a six-digit code is a credential-stuffing hole |
| `Idempotency-Key` replay protection | **Fail closed** (503) | Replaying a payment is worse than a retryable error |

The rate limiter is a token bucket implemented as a Lua script, so the read-modify-write is
atomic on the server. Separate `GET`/`SET` calls would let bursts slip through under
concurrency, which is exactly when a limiter matters.

The OTP attempt counter lives here rather than in a database column for a specific reason: a
failed login rolls its transaction back, which would discard a column increment and leave the
retry budget permanently unused. See
[ADR 0004](adr/0004-otp-attempt-counter-in-redis.md).

Cache invalidation is event-driven, not TTL-driven. Menu TTL is a ceiling; an item going out of
stock deletes the entry immediately, because continuing to sell food a kitchen cannot make is
the failure this cache would otherwise cause.

## Kafka — event streaming

Nine topics, one per bounded context, partitioned by `aggregate_id` so per-aggregate ordering
holds. Producers are idempotent; consumers commit offsets manually after handling, so a crash
mid-handler causes a redelivery (absorbed by the deduplication table) rather than a lost event.

A managed service (MSK, Confluent Cloud, or Azure Event Hubs' Kafka interface) is the intended
production deployment. Self-hosting Kafka is a full-time job that does not differentiate a
delivery platform.

Locally, the `memory` backend is the default so the whole stack runs without a broker; the
Compose stack includes Kafka in KRaft mode for exercising real cross-service flow.

## Time-series store for tracking — recommendation

Courier location arrives every 1–5 seconds per active courier. At 500 concurrent couriers that
is roughly 100–500 writes per second sustained, 10–40 million points per day, almost all of it
read once (live tracking) and then only in aggregate (route replay, ETA model training).

Putting that in the transactional PostgreSQL instance would let a background workload compete
with order writes for the same buffer cache and WAL.

**Recommendation: TimescaleDB on a separate PostgreSQL instance.**

- Hypertables partition by time automatically, and continuous aggregates give cheap
  per-minute rollups for the ETA model.
- Native compression on older chunks is roughly 10–20x, which makes a 90-day retention
  affordable.
- PostGIS works inside it, so route geometry queries use the same functions as the rest of the
  platform.
- It is still PostgreSQL: the same driver, the same migration tooling, the same operational
  knowledge. Nobody has to learn a second query language.

Alternatives considered. **ClickHouse** is faster for large analytical scans and would win if
the primary use were offline analysis, but it is a second operational system with different
semantics, and it is a poor fit for the live per-order lookup that tracking needs. **Cassandra
or DynamoDB** handle the write rate easily but make time-range and geospatial queries awkward,
which is most of what this data is for. **Redis streams** are attractive for the live tail —
and are the right place for last-known-location — but are not a durable historical store.

Concretely: last-known courier location in Redis (a single key per courier, sub-millisecond
reads for the live map), the full history in TimescaleDB.

## Object storage — images

S3-compatible (MinIO locally, S3 or equivalent in production) for merchant logos, hero images
and menu item photography. Uploads go direct from client to bucket using pre-signed URLs, so
image bytes never pass through the API; the services only ever store and serve URLs. A CDN
sits in front, and derivatives (thumbnails, WebP) are generated on write rather than on read.

## Backups and retention

| Store | Backup | Retention |
|---|---|---|
| PostgreSQL | Continuous WAL archiving, point-in-time recovery | 35 days PITR |
| Redis | None; every key is reconstructible | n/a |
| Kafka | Replicated across availability zones | 7 days, except `notification.events` at 24 hours because it carries OTP codes |
| TimescaleDB | Daily snapshot | 90 days raw, aggregates indefinitely |
| Object storage | Versioning plus cross-region replication | Indefinite |

Personal data deletion (a UAE PDPL erasure request) is a documented cross-service workflow, not
a single `DELETE`: it touches `identity`, `auth`, `orders` and the analytics warehouse, and
order records must be retained for tax purposes with the personal fields redacted rather than
removed. That workflow is specified alongside the order service in Step 2, when there are
orders to redact.
